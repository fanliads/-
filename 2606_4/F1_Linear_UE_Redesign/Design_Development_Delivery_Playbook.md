# 产品设计到开发交付标准流程

> 目标：保证需求、原型、开发实现和最终验收使用同一套语言，避免“功能完成但交付不像原型”。

## 1. 流程总览

```text
迭代立项
  → 需求背景确认
  → 业务流程与对象定义
  → 页面结构确认
  → 交互原型确认
  → PRD 冻结
  → 开发交底
  → 实现追踪
  → 开发自测
  → 视觉与功能验收
  → UAT
  → 迭代复盘与归档
```

每个箭头都是阶段门禁。上一个阶段没有明确确认，不得进入下一个阶段。

## 2. 角色与职责

| 角色 | 核心职责 | 不应代替的职责 |
|---|---|---|
| 产品负责人 | 业务目标、范围、对象语义、验收口径 | 不代替开发决定技术实现 |
| 交互/视觉设计 | 页面结构、状态、行为和视觉规格 | 不擅自改变业务流程 |
| 开发负责人 | 技术方案、接口映射、实现风险 | 不自行删减未确认的产品能力 |
| 测试负责人 | 用例、回归、异常场景和证据 | 不只验证页面能打开 |
| 业务验收人 | 按真实工作场景完成 UAT | 不用口头反馈替代验收记录 |

## 3. Phase 0：迭代初始化

必备动作：

1. 为迭代分配唯一编号，例如 `2607_1`。
2. 在根目录 `ITERATION_LOG.md` 登记迭代。
3. 创建迭代级 `Requirement_List.md`。
4. 每个需求使用独立编号和目录，例如 `F1_Requirement_Pools`。
5. 明确上一迭代是有效基线、参考资料还是已废弃材料。

退出条件：迭代编号、需求编号、负责人和目标已登记。

## 4. Phase 1：需求背景与范围

必须产出：

- 问题背景。
- 用户与场景。
- 业务目标和非目标。
- 当前流程与目标流程。
- 业务对象及对象关系。
- 约束、风险与依赖。
- 历史能力清单。

关键规则：不能只写“优化页面体验”。必须说明哪些业务行为保持不变、哪些行为被替换。

退出条件：产品负责人确认背景和范围。

## 5. Phase 2：业务与页面设计

必须产出：

- 用户故事。
- 用户旅程。
- 业务流程图。
- 页面结构。
- 字段字典。
- 状态机。
- 权限矩阵。
- 异常场景。

每个页面至少定义：

- 页面目的。
- 默认视图。
- 搜索范围。
- 筛选项。
- 列表字段与字段顺序。
- 可编辑字段及保存方式。
- 详情信息顺序。
- 空状态、加载态、错误态和无权限态。

退出条件：对象、状态、字段和页面结构没有冲突项。

## 6. Phase 3：原型设计与评审

原型必须覆盖：

- 默认数据状态。
- 空状态。
- 长标题和大量标签。
- 浮层、抽屉、弹窗和详情页。
- 新建、编辑、删除、拒绝等关键动作。
- 键盘行为和 hover 行为。
- 接口失败或提交失败的反馈。

评审状态统一使用：

| 状态 | 含义 |
|---|---|
| Draft | 设计中，不可开发 |
| Ready for Review | 可评审，不可开发 |
| Changes Requested | 需修改，不可开发 |
| Confirmed | 已确认，可进入 PRD 冻结 |
| Superseded | 已被新版替代 |

关键规则：只有 `Confirmed` 原型能成为开发基线。

退出条件：评审日志包含确认人、确认时间、确认版本和遗留项。

## 7. Phase 4：PRD 冻结与需求追踪

PRD 必须将原型中的关键行为文字化，不能只放原型链接。

开发前建立追踪矩阵：

| ID | PRD 条款 | 原型位置 | 数据字段/API | 代码模块 | 验收用例 | 状态 |
|---|---|---|---|---|---|---|
| RP-001 | 行点击进入详情 | 原型列表行 | detail API | RawPoolView | UAT-RP-01 | Pending |

变更规则：

- PRD 和原型冲突时停止开发，由产品负责人决策。
- 新增或删除能力必须留下变更记录。
- 口头决定必须在当天补充到文档。
- 原型更新后必须更新版本号或更新时间。

退出条件：追踪矩阵无未决冲突，PRD 状态为 Confirmed。

## 8. Phase 5：开发交底

交底会议必须逐项确认：

1. 本次范围和明确不做的内容。
2. 唯一原型入口和版本。
3. 历史功能的保留、迁移和删除。
4. 页面状态、字段、权限和接口。
5. 视觉断点和固定验收视口。
6. 技术风险和分批策略。
7. 验收人、验收环境和交付日期。

开发任务必须按页面和能力拆分，不能用“完成需求池页面”作为单一任务。

退出条件：开发负责人确认可实现性，测试负责人确认可测试性。

## 9. Phase 6：开发实施

推荐顺序：

1. 页面壳和 Design Tokens。
2. 静态结构与响应式布局。
3. 基础组件和浮层规则。
4. 列表、分组和字段编辑。
5. Peek、Drawer、Detail。
6. 新建、拆分、拒绝等业务动作。
7. 接口、权限和异常反馈。
8. 空状态和边界状态。

实现规则：

- 不凭感觉改造原型。
- 无法实现或成本异常时先提变更，不自行替代。
- 每完成一个追踪矩阵条目就更新状态。
- 公共组件不能牺牲页面级视觉还原。
- 不通过隐藏功能来解决布局问题。

## 10. Phase 7：开发自测

### 10.1 静态检查

- 类型检查。
- Lint 和格式检查。
- 生产构建。
- 控制台错误。
- 未使用代码和重复样式。

### 10.2 功能检查

- 搜索字段覆盖范围。
- 筛选组合和重置。
- 就地编辑成功、失败和撤销。
- 新建后立即可见。
- 删除、拒绝、作废有二次确认或原因。
- 权限控制前后端一致。
- 快速重复点击不会重复提交。

### 10.3 视觉检查

固定视口至少包括：

- 1435 × 931：设计原型基准。
- 1280 × 800：常规笔记本。
- 1920 × 1080：大屏。

逐项比较：

- 页面壳宽度。
- 标题和工具栏高度。
- 字段顺序和列宽。
- 行高、间距、边框和颜色。
- 浮层位置和层级。
- 长标题、空状态和滚动行为。

退出条件：所有差异都有截图证据或明确接受记录。

## 11. Phase 8：测试与 UAT

测试证据至少包含：

- 用例编号。
- 操作步骤。
- 预期结果。
- 实际结果。
- 截图或录屏。
- 测试数据。
- 浏览器和视口。
- 缺陷链接。

缺陷等级：

- Blocker：基线未确认、核心流程不可用、数据损坏。
- High：主要能力缺失、严重布局错位、权限越权。
- Medium：次要功能异常、局部视觉偏差。
- Low：文案、微小间距或非阻断体验问题。

UAT 必须由真实业务角色使用测试数据完成，不能由开发自测代替。

退出条件：Blocker/High 为零，业务验收人签字。

## 12. Phase 9：迭代收尾

必须完成：

1. 更新 `Requirement_List.md`。
2. 更新根目录 `ITERATION_LOG.md`。
3. 记录最终原型、PRD、代码版本和测试环境。
4. 归档视觉基线截图和 UAT 证据。
5. 登记遗留问题和下一迭代入口。
6. 完成复盘：做对了什么、出了什么问题、流程如何调整。

## 13. Definition of Ready

需求进入开发前必须全部满足：

- 目标、范围和非目标明确。
- 唯一 PRD 与原型入口明确。
- 原型状态为 Confirmed。
- 历史能力取舍已记录。
- 字段、状态、权限和接口已定义。
- 异常和空状态已设计。
- 追踪矩阵无待决项。
- 验收环境、验收人和验收视口已确定。

## 14. Definition of Done

需求完成必须全部满足：

- 追踪矩阵全部完成。
- 类型检查、构建和自动测试通过。
- 功能、视觉、权限和异常场景均通过。
- 原型对照截图已归档。
- 没有 Blocker/High 缺陷。
- UAT 已签字。
- PRD、原型、代码和迭代台账已同步。

## 15. 本次迭代的核心经验

1. **原型确认是开发授权，不是参考建议。**
2. **历史原型和新版原型必须明确“继承与覆盖”，不能混合取用。**
3. **视觉重构不能默认删除业务能力。**
4. **构建成功只证明代码可打包，不证明产品交付正确。**
5. **每个 PRD 条款都要能追溯到原型、代码和测试用例。**
6. **先验收结构，再接复杂接口，可以更早发现方向错误。**
7. **任何未确认的主观优化都会扩大最终验收差异。**
8. **测试环境必须在交付前准备好，并提供稳定、可重复的启动方式。**
