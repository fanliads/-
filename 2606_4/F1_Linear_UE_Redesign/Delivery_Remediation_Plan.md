# 需求池交付整改计划

> 适用范围：`2606_4 / F1_Linear_UE_Redesign`
> 整改对象：原始需求池、产品需求池
> 当前结论：生产实现不可按“验收通过”处理，必须重新经过基线确认、差异收敛和 UAT。

## 1. 当前问题定性

本次偏差不是单纯的视觉细节问题，而是交付流程失控：

1. `Page_Review_Log.md` 中的页面状态仍是 `Ready for review` 或 `Updated for review`，没有任何 `Confirmed` 记录。
2. `Requirement_List.md` 明确要求“原型确认前不修改生产 Vue”，但生产实现已经开始。
3. 实施过程中同时引用了 `2605_1`、`2606_3`、`2606_4` 三套材料，没有形成唯一的基线与覆盖关系。
4. 验收主要验证了构建、接口和局部点击，没有验证原型结构、视觉和完整交互。
5. 当前代码已经出现表头与单元格条件错位，说明交付前缺少逐字段映射检查。

## 2. 整改原则

- 不直接在当前页面上继续打补丁。
- 先确认“什么是正确结果”，再进入代码整改。
- `2605_1` 作为历史业务能力清单，不默认等于本次视觉基线。
- `2606_4` 只有在原型正式确认后，才能成为实施基线。
- 任一历史能力如被删除或替换，必须在差异矩阵中写明依据并获得确认。
- 构建成功不等于验收成功；功能、视觉、数据和权限必须分别验收。

## 3. 建议的基线关系

> 2026-07-14 已确认：`2605 保能力、2606_4 定交互`。

| 材料 | 建议角色 | 使用规则 |
|---|---|---|
| `2605_1/F1_ReqMgmt/Prototypes` | 历史业务能力基线 | 用来检查 AI 定级、拆分、分组、字段设置等能力是否丢失 |
| `2606_3/F1_整体UE升级` | 当前系统上下文 | 只用于理解现有接口和存量实现，不作为本次审批证据 |
| `2606_4/F1_Linear_UE_Redesign/Prototypes` | 候选交互与视觉基线 | 必须完成页面级确认后才能实施 |
| `Requirement_Pools_PRD.md` | 需求语义基线 | 解释对象、流程和验收规则；与原型冲突时必须提请决策 |
| 生产 Vue 与 API | 技术实现约束 | 不得反向改变已确认的产品语义 |

建议最终规则：**2605 保能力、2606_4 定交互，明确覆盖的旧能力才允许移除。**

## 4. 立即执行顺序

### Gate 0：冻结与确认（已通过）

在完成以下确认前，不继续修改两个需求池：

- 确认本次视觉与交互是否以 `2606_4/Prototypes` 为准。
- 确认 `2605_1` 中哪些能力必须保留。
- 确认行点击是“完整详情页”还是“常驻右侧详情栏”。
- 确认产品池分组采用业务分发阶段还是 Linear 状态分组。
- 将确认结果写入 `Page_Review_Log.md`，状态改为 `Confirmed`。

输出：基线决策已写入 `Page_Review_Log.md`，后续所有整改按追踪矩阵执行。

### Gate 1：建立需求追踪矩阵

逐条登记：

- 页面区域。
- 原型位置。
- PRD 条款。
- 历史能力。
- 当前实现位置。
- 处理结论：保留、替换、删除、新增。
- 验收方式和负责人。

任何标记为“待确认”的条目不得进入开发。

输出：`Implementation_Traceability_Matrix.md`。

### Gate 2：完成结构还原

只处理页面骨架，不接复杂业务动作：

1. 全局导航和页面壳。
2. 顶部单行工具栏。
3. 列表宽度、字段顺序、行高和分组。
4. Filter、Display、Peek、Drawer、Detail 的层级关系。
5. 空状态、长标题和窄屏状态。

验收方式：固定视口截图对照，结构与视觉通过后再接功能。

### Gate 3：完成业务功能映射

原始需求池至少核对：

- 搜索和筛选。
- 列表字段及就地编辑。
- 拒绝原因。
- 日期选择器。
- 业务提交、业务判定。
- AI 定级是否保留。
- 需求拆分和关联产品需求。
- 历史活动记录。

产品需求池至少核对：

- 顶部新建和分组新建。
- 分组、折叠与视图切换。
- 用户故事、PM 分析、追加说明。
- 父原始需求预览。
- 迭代、PRD、处理人和业务线编辑。
- 未排期的独立筛选语义。
- 作废、阻塞、拒绝等异常状态原因。

输出：功能验收记录和接口契约检查结果。

### Gate 4：联合验收

按以下顺序验收：

1. 产品负责人做原型一致性验收。
2. 开发做接口、权限和异常场景自测。
3. 测试执行完整场景用例。
4. 业务方在测试环境做 UAT。
5. 所有问题关闭后才能记录为 `Accepted`。

## 7. 本次整改完成定义

只有同时满足以下条件，才能重新交付：

- 基线原型状态为 `Confirmed`。
- 需求追踪矩阵无待确认项。
- 两页不存在传统操作列，除非确认恢复历史业务动作。
- 所有保留的历史能力都有实现或明确迁移入口。
- 原型关键页面在固定视口下完成截图对照。
- 搜索、筛选、编辑、Peek、详情、Drawer、创建、拆分全部有用例。
- 空状态、长标题、无权限、接口失败、重复提交均完成验证。
- 构建、类型检查、接口回归、权限回归和 UAT 全部通过。
