# F2 迭代管理优化—需求背景

> 状态：待确认

## 1. 需求概述

现有系统已具备迭代数据和需求所属迭代字段，但创建迭代时只能选择“单周”或“双周”，周期被固定为整周。实际业务中会出现临时迭代、短期修复窗口或跨非整周日期的交付安排，现有模型无法准确表达。需要将迭代周期改为可配置的起止日期，并让产品经理集中管理迭代生命周期、安排未排期需求，从计划直接进入看板跟踪执行。

### 1.1 目标用户

- 核心用户：产品经理。
- 决策用户：产品负责人。
- 查看用户：项目经理及获得迭代访问权限的相关角色。

### 1.2 核心价值

- 建立从未排期需求到迭代交付的规划闭环。
- 兼容常规节奏与临时迭代，避免为了适配固定周数而填写失真的周期。
- 提供统一的迭代进度和基础容量视角。
- 降低需求跨迭代调整及迭代收尾的操作成本。

## 2. 初步需求假设

- 迭代状态采用“未开始、进行中、已完成、已归档”。
- 迭代至少包含名称、团队、开始日期、结束日期、目标和状态；周期天数由起止日期计算。
- “单周”“双周”作为日期快捷预设保留，用户也可直接选择任意开始和结束日期。
- 临时迭代不要求从周一开始、在周日结束，也不要求持续天数为 7 的整数倍。
- 产品经理可从未排期区批量加入需求，也可将需求移出或迁移到其他迭代。
- 迭代详情呈现需求总量、各状态数量、完成比例和基础工作量信息。
- 已完成迭代默认只读；未完成需求在完成操作中必须明确迁移去向。
- 迭代列表和详情均使用单一全宽主内容区，不使用右侧常驻详情或辅助判断栏。

## 3. Core Scenarios

### 3.1 创建并启动迭代

1. 产品经理进入迭代管理并新建迭代。
2. 选择“单周”“双周”快捷周期，或直接设置任意开始日期和结束日期。
3. 系统根据日期实时计算并展示周期天数，不再用周期类型反向限制日期。
4. 用户填写名称、目标和团队信息。
5. 从未排期需求中选择需求加入迭代。
6. 核对范围后启动迭代，系统记录启动时间与操作者。

### 3.2 创建临时迭代

1. 产品经理因临时修复或专项交付发起新建迭代。
2. 直接选择实际的开始日期和结束日期，例如 3 天、10 天或跨自然周区间。
3. 系统校验结束日期不早于开始日期，并检查必要字段。
4. 用户保存后，迭代列表、详情、需求排期入口和看板均展示真实日期区间。

### 3.3 迭代中调整范围

1. 产品经理打开进行中的迭代。
2. 查看需求状态分布和当前工作量。
3. 将新增需求加入迭代，或将不再交付的需求移出/迁移。
4. 系统记录范围变化，并同步到产品需求池和看板。

### 3.4 完成迭代

1. 产品经理发起完成迭代。
2. 系统列出尚未完成的需求。
3. 用户选择移至未排期或迁移到目标迭代。
4. 系统完成迁移、冻结本期统计，并将迭代设为已完成。

## 4. 范围边界

### 本期包含

- 迭代列表/详情、创建编辑、启动完成归档、需求排期与迁移、进度和基础容量提示。
- 任意起止日期、周期天数自动计算，以及单周/双周快捷预设。
- 对已有单周/双周迭代保持兼容，历史起止日期和展示结果不发生变化。

### 本期暂不包含

- 自动排期、资源成本核算、燃尽图预测、跨团队依赖网络与项目集管理。
- 选中迭代后在列表右侧展开常驻详情/判断面板的分栏结构。

## 5. 待确认问题

- 是否允许多个迭代同时处于进行中？
- 容量以需求数量还是工作量点数为主？
- 进行中迭代增删需求是否需要二次确认或审批？
- 完成迭代时，未完成需求默认回到未排期还是必须选择目标迭代？
- 临时迭代是否需要独立类型标识；当前建议不增加强制类型，仅以自定义日期表达，避免增加不必要的分类。

## 6. 周期规则与验收口径

- 用户可以创建任意合法起止日期的迭代，包括不足 7 天、超过 14 天和跨非整周的周期。
- 开始日期和结束日期均计入周期天数；同一天起止时按 1 天计算。
- 结束日期早于开始日期时禁止保存，并在日期字段附近提示原因。
- 修改开始或结束日期后，系统立即重新计算周期天数。
- 选择单周/双周预设时自动带出日期，用户继续修改日期后按自定义周期保存。
- 列表、详情、选择器和看板中的迭代周期均以真实起止日期为准。
- 既有迭代无需人工迁移；若历史记录含周期枚举，仍以已有起止日期作为展示和计算依据。

## 7. 页面结构验收约束

- 迭代列表使用全宽列表；点击迭代进入独立的全宽迭代详情页。
- 迭代详情内可通过页签或主内容区分段组织“概览、需求、进度”，不在右侧附加第二详情栏。
- 新建/编辑迭代、需求排期和迁移可使用居中弹窗，但不得形成持续占位的右侧栏。
- 选中列表项前后，主列表宽度必须保持一致。
