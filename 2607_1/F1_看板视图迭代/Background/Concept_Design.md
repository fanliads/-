# F1 看板视图迭代—概念设计

> 状态：已确认（2026-07-20）
> 前置依据：`Requirement_Background.md`、`System_Survey.md`

## 1. 设计命题

在不引入右侧常驻详情栏的前提下，同时支持原始需求和产品需求，让用户快速查看状态分布、筛选卡片、任意拖拽状态，并能进入完整详情后无损返回工作现场。

## 2. 共同约束

- 主工作区始终全宽，选中卡片不得压缩列宽。
- 原始需求和产品需求使用各自的状态集合，不混在同一套列中。
- 状态允许任意互转，仍执行现有权限校验。
- 完整详情由已有独立详情页承载。
- 本期不改角色权限、不建设工作流编辑器。

## 3. 方案 A：单页双对象看板

### 概念

保留一个“看板视图”页面，在标题区下方使用“原始需求 / 产品需求”分段切换。切换后复用同一套全宽看板骨架，但加载对应对象的状态列、筛选项和卡片字段。

### 页面骨架

1. 页面标题与数量摘要。
2. 对象类型切换：原始需求 / 产品需求。
3. 主工具栏：搜索、优先级、业务线、负责人、所属迭代（仅适用时）、清除筛选。
4. 全宽状态列区域。
5. 卡片快捷菜单与居中确认弹窗。

### 优点

- 用户只需理解一个看板入口，切换成本低。
- 两类对象可共享布局、拖拽反馈、空状态和上下文恢复机制。
- 与当前看板已有对象切换方式一致，改造范围可控。
- 未来统一优化筛选或卡片密度时维护成本更低。

### 缺点

- 两类对象字段差异较大时，工具栏需要动态变化。
- 若状态列很多，仍需横向滚动和明确的滚动提示。
- 用户可能误以为两类对象能在同一看板混排，需要在视觉上强化当前对象。

## 4. 方案 B：两个独立看板页面

### 概念

将原始需求看板和产品需求看板拆成两个独立路由及页面入口，各自拥有专属工具栏、状态列和卡片结构。

### 页面骨架

- 原始需求看板：原始需求专属筛选、状态列和详情跳转。
- 产品需求看板：迭代筛选、产品需求专属字段、状态列和详情跳转。

### 优点

- 每个页面更聚焦，可完全按对象特征设计。
- 路由和权限边界更直观，便于分享具体视图链接。
- 不需要处理大量动态字段切换。

### 缺点

- 入口和页面数量增加，用户在两个看板间切换更慢。
- 两套页面容易出现交互和视觉不一致。
- 公共能力重复建设，后续维护成本较高。
- 偏离当前统一看板入口的使用习惯。

## 5. 方案选择

选择 **方案 A：单页双对象看板**。

### 选择理由

- 最符合“保持现有能力并修正页面结构”的迭代定位。
- 用户已经确认看板同时支持两类需求，单页切换更容易建立统一心智。
- 能最大化复用全宽布局、拖拽、筛选和上下文恢复能力。
- 无需引入红框所示的详情侧栏，完整详情统一跳转至独立页面。

## 6. 关键设计决策

### 6.1 分组方式

- 首版只按状态分组。
- 负责人、优先级、业务线作为筛选条件，不在本期增加多维分组，避免横向结构和卡片迁移语义复杂化。

### 6.2 卡片信息

- 通用：编号、标题、优先级、负责人。
- 原始需求：补充业务线、来源。
- 产品需求：补充所属迭代；工作量仅在已有字段可靠时展示。
- 不在卡片内堆叠长描述、判断结论或完整字段宫格。

### 6.3 状态拖拽

- 任意状态列之间可拖拽。
- 乐观移动卡片，同时提交状态更新。
- 保存失败时回滚原列并提示原因。
- 无编辑权限时保留查看能力，但不显示可拖拽反馈。

### 6.4 详情访问

- 单击卡片进入对应独立详情页。
- 返回看板时恢复对象类型、筛选、横向/纵向滚动位置。
- 快捷字段编辑使用卡片菜单或居中弹窗，不出现右侧常驻栏。

## 7. 不选择的结构

- 不采用右侧固定详情/判断面板。
- 不采用原始需求与产品需求混排的统一状态列。
- 不在首版提供自定义分组、泳道、保存多个私人视图。
